# ARCHITECTURE — 本记忆系统的设计与教训

> **按需读取。** 只在要改这套记忆系统本身、或需追溯某个设计决策时读。
> 常驻文件是 `AGENTS.md` + `INDEX.md`；本文件不在常驻里。

---

## 1. 为什么这样分层

**要解决的问题**：AI 每次开新对话都失忆；把所有历史塞进一个文件又会检索困难、上下文浪费。

**核心设计**：把"**常驻**"和"**按需**"严格分开。

| 层 | 文件 | 何时读 | 大小约束 |
|---|---|---|---|
| 入口 | `AGENTS.md`（DSH 自动注入）、`INDEX.md` | **每次** | 合计 ≤ 10 KB |
| 项目状态 | `projects\<项目>\STATE.md` | 只读当前那**一个** | ≤ 8 KB |
| 规则细节 | `SCHEMA.md`、`GLOBAL_RULES.md` | 用到才读 | 不限 |
| 历史资料 | `import\` | 信息不足才查 | **冷藏，永不增长** |

**关键性质**：**每次对话的 token 开销与记忆库总量无关。** 加第 12、100 个项目，不会让每次对话多花一个 token。

## 2. 关键机制：只有两条路能自动注入上下文

经实测（DSH `<pkg-version>`）：

1. **`AGENTS.md` / `CLAUDE.md` 自动加载**（`dsh-agent-instructions`，`dsh-base` 默认挂载，上限 65536 B）
   —— 用户全局 `$DSH_HOME\AGENTS.md` + 项目根到 cwd 的每一级。**首请求即注入。**
2. **Hook 钩子桥**（`dsh-hooks-claude-code`）—— **当前未挂载**。

**Skill 不会自动运行。** 它只在模型主动调用 `skill` 工具时才加载正文，是"说明书"不是"自动化"。

**做不到的**（CC 桥不支持）：`SessionEnd`、`PreCompact`、`PostCompact`。
→ **"对话结束自动归档""压缩前自动出交接包"需要写原生 Cordis 插件**，配置解决不了。

## 3. 工作区沙箱边界（已实测）

| 位置 | 读 | 写 |
|---|---|---|
| `<path>`（工作区） | ✅ | ✅ |
| 工作区外（桌面、F 盘） | ✅ | ❌ **需逐次批准** |

**所以记忆规范源必须在工作区内**，否则每次写入都要人工批准，自动化闭环不可持续。

## 4. 六项历史冲突与丢失（导入时发现）

| # | 内容 | 结论 |
|---|---|---|
| 1 | 旧资料写记忆根目录是 `Desktop/<旧目录名>` | **该目录不存在**——根目录早已改名。典型"旧摘要被当当前事实" |
| 2 | 一份库**丢失**了另一份的若干项内容（角色分工的新决定、外接盘符、学习方向、语言偏好、"不得只凭静态审查宣称功能正常"等） | 已补回 `GLOBAL_RULES.md`，逐条标 `[仅交接包含]` 以便追溯 |
| 3 | 外接盘符：历史记录 `F:` vs 新记录 `H:` | 采用新记录，并立规则"旧盘符不得当作当前路径"；仍待插入设备核实 |
| 4 | 数据根迁移是否切换 | **实测确证未切换**（环境变量仍指旧根；迁移脚本与目录缺失） |
| 5 | 第三方插件清单过时（旧审计说只有 2 个，实际 4 个） | 已记录实测值 |
| 6 | 交接包 manifest 自检 | ✅ 29/29 通过。**但过程中我误报过一次不匹配——原因是我自己往被清单覆盖的文件加了注记横幅。教训见下。** |

## 5. 踩过的坑与规则

**（1）绝不修改被完整性清单覆盖的文件。**
注释、更正、整理一律写到**独立的元数据文件**里。
（我曾在 `import` 里加"导入注记"横幅，导致 manifest 校验失败并**误报**为数据损坏。）

**（2）报告"完整性失败"前先确认是不是自己造成的。**

**（3）`icacls /deny` 会替换而非叠加继承权限。**
未先 `/grant` 读权限就 `/deny` → 该目录继承权限被顶掉 → `os.walk` 读到 **0 文件**，
而且那条 DENY **挡住了移除它自己所需的权限**（`/remove:d` 也失败），只能提权撤销。
→ **规则：先 `/grant` 显式读权限，再 `/deny` 只拒写；改完立即用 `os.walk` + 基线双重复验。**
（已实际发生一次，零文件损失。）

**（4）`ReadOnly` 文件属性防不住删除。** 实测可删。要真保护只能走 ACL。

**（5）哈希基线有两种相反用途。**
**冻结保护**：报差异 = 报警。**变更侦测**：报差异 = 正常工作（对方在写）。
用错会得出完全相反的结论。建基线前先想清楚是哪一种，并写进对应 `STATE.md`。

**（6）证据标记的格式错误（设计缺陷）。**
我把状态和来源塞进同一个 `[status: X | source: Y]` 括号，导致容易只顾一个：
一个会话写了 `[status: derived | source: derived]`（`derived` 是**来源词**，不该在 status 位）。
→ **已改为推荐两个标记分开写**：`[status: …]` `[source: …]`，且**两个都必须有**。
自检工具现在能精确报出"来源词被写进状态位置""数量不配对"。

**（7）自检工具必须能抓错，否则等于没有。**
`memory-check.py` 用故意做坏的文件验证过：假 API key、空口声称 `test-passed`、非法状态词、配平错误——**全部抓到**。

**（8）自检工具不能误报。**
它曾把我**引用**坏格式的更正说明当成真错误。
→ **已修：校验前先剥离行内代码与代码块**（`strip_inline_code`）。

## 6. 并发现实

本机**同时有多个 Harness 会话**，且**已发生两个会话同时写同一个项目文件**。
实测证据：某项目的 `STATE.md` 在一个会话准备写入时，已被另一会话创建并维护；
`storages\session_projcache\sessions\` 下同时有 4 个活跃会话。

**规则**：写记忆一律**先读后写、写后回读**；发现他人内容**追加不覆盖**；同一主题**只用一个会话**。

## 7. 当前未做 / 已知限制

- **无失败自动通知**：靠自检脚本 + 主动报告。
- **无跨模型导出包**（导出时必须排除 `$DSH_HOME`——内含明文 API Key）。
- **无会话归档**（`archive\` 未建立）；需 `session/disposed` 原生插件。
- **`compaction/*` 事件存在但未接**（原生插件才能用）。
- **`import\` 是静态冷藏区**，不增长也不参与检索。
